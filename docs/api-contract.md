# MyVivahAI — External API Contract

## Overview

To integrate the Real-Time Chat widget, each client platform must expose a set of HTTP APIs that MyVivahAI can call. These are **the client's own APIs**, exposed on the client's infrastructure, and configured by the client in the API Integration dashboard.

This document defines the **contract** each capability must satisfy. Parameter/field names are recommendations; the field-mapping feature allows clients to comply without exact-name matching.

---

## Terminology

| Term | Meaning |
|---|---|
| External User | A user on the client platform (e.g., a bride, groom, or family member) |
| External User ID | The client platform's own identifier for a user |
| Platform | The client platform (registered on MyVivahAI) |
| Capability | A required or optional API that the client exposes |

---

## Denotation Legend

- **Required immediately** — must be implemented before integration goes live.
- **Optional** — recommended but not mandatory; absence changes available features.
- **Future** — may be required later; not for MVP.

## Capability 1: User Identity / Current User API

**Purpose:** Identify the currently logged-in user. MyVivahAI calls this API with a reference token (or session) so the client platform can resolve "who is the current user."

**Status:** Required

### Request

| Field | Suggested | Notes |
|---|---|---|
| Method | GET | |
| Path | `/api/v1/current-user` | Configurable |
| Auth | Bearer token or custom header | The token is generated by the client's frontend integration |
| Headers | Reference token identifying the session | |

### Response (Success)

```json
{
  "success": true,
  "data": {
    "id": "user_12345",
    "name": "Riya Sharma",
    "email": "riya@example.com",
    "phone": "",
    "profile_photo_url": "https://cdn.example.com/riya.jpg"
  }
}
```

### Response (Failure)

```json
{
  "success": false,
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Invalid or expired session"
  }
}
```

### Validation Rules

- `id` is required.
- `name` is required.
- `email`, `phone`, `profile_photo_url` are optional; at least one of them recommended.
- If `success` is `true`, `data.id` must be a non-empty string.
- The client is responsible for the token → user resolution.

## Capability 2: User Details API

**Purpose:** Fetch details of any external user by ID. Used by the widget to render contact/profile information for a conversation peer.

**Status:** Required

### Request

| Field | Suggested | Notes |
|---|---|---|
| Method | GET | |
| Path | `/api/v1/users/{id}` | Configurable |
| Auth | Bearer token or custom header | Platform-level credential |

### Response (Success)

```json
{
  "success": true,
  "data": {
    "id": "user_67890",
    "name": "Aarav Mehta",
    "email": "aarav@example.com",
    "phone": "+91 98765 43210",
    "profile_photo_url": "https://cdn.example.com/aarav.jpg",
    "is_online": true
  }
}
```

### Response (Failure)

```json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User not found"
  }
}
```

### Validation Rules

- `id` and `name` required.
- `profile_photo_url` strongly recommended (the chat widget shows an avatar).
- Return HTTP 404 with the failure body when a user is not found.

### Which Fields Are Actually Required by the Chat Widget

| Field | Required | Why |
|---|---|---|
| `id` | **Yes** | Identifies the user |
| `name` | **Yes** | Display name in conversations/contacts |
| `profile_photo_url` | Recommended | Avatar display; fallback to initials |
| `email` | No | Only if widget shows email |
| `phone` | No | Only if widget shows/links phone |
| `is_online` | Recommended | For presence indication |

## Capability 3: User Search API

**Purpose:** Let the chat widget search users on the external platform (by name, etc.).

**Status:** Required

### Request

| Field | Suggested | Notes |
|---|---|---|
| Method | GET | |
| Path | `/api/v1/users/search` | Configurable |
| Auth | Bearer token or custom header | |
| Query Parameters | `q` (search term), `limit`, `offset` | Configurable |

### Response (Success)

```json
{
  "success": true,
  "data": [
    {
      "id": "user_111",
      "name": "Kabir Singh",
      "profile_photo_url": "https://cdn.example.com/kabir.jpg"
    },
    {
      "id": "user_222",
      "name": "Kabir Khan",
      "profile_photo_url": "https://cdn.example.com/kabir-khan.jpg"
    }
  ],
  "meta": {
    "total": 2,
    "limit": 20,
    "offset": 0
  }
}
```

### Validation Rules

- `data` must be an array.
- Each item must include `id` and `name`.
- If the external platform does not implement search, this capability is a blocker for the widget's search feature. (**Open decision:** whether search can be made optional at MVP.)

## Capability 4: Chat Permission API *(Optional)*

**Purpose:** Let the client platform control who can communicate with whom (e.g., age-match filters, paid members only, etc.). If not provided, MyVivahAI allows any conversation between any two users of the same platform.

**Status:** Optional attribute of the integration configuration.

### Request

| Field | Suggested | Notes |
|---|---|---|
| Method | GET | |
| Path | `/api/v1/can-chat` | Configurable |
| Auth | Bearer token or session token | |
| Query Parameters | `from_user_id`, `to_user_id` | Configurable |

### Response

```json
{
  "success": true,
  "data": {
    "allowed": true,
    "reason": null
  }
}
```

```json
{
  "success": true,
  "data": {
    "allowed": false,
    "reason": "Premium membership required"
  }
}
```

### Behavior When Not Configured

- MyVivahAI assumes chat is allowed between any two platform users.
- The dashboard shows the capability as "Optional / Not configured."

## External User Identity & Mapping (Phase 3B-2)

The `id` returned by **Capability 1** (and used in Capability 2/3) becomes the canonical `external_user_id` that MyVivahAI stores. It keys a platform-scoped identity reference map (`platform_external_user_map`), so MyVivahAI can resolve "who this user is" without ever copying the client's profile data.

Requirements this places on the client's `id` values:

| Rule | Reason |
|---|---|
| Stable for the life of the user | The map is keyed on it; changing it orphans prior conversation references |
| Unique **within** the platform | `(platform_id, external_user_id)` is a DB-level unique constraint |
| May repeat across platforms | The same raw value on two different platforms is two distinct identities |
| URL-safe, no `/` | Used as a path segment in MyVivahAI's own `GET /api/v1/users/{external_user_id}` |

MyVivahAI's own identity endpoints (server-to-server, PASETO-authenticated) are documented in `integration-api.md`.

## Authentication Options for Client APIs

| Option | Description | Recommended |
|---|---|---|
| None | Public endpoint | Testing only |
| Bearer Token | Static token in `Authorization` header | For server-to-server |
| API Key | Key in header or query parameter | Simple |
| Custom Header | Arbitrary header (e.g., X-Platform-Key) | Flexible |
| HMAC Signed | Request signed with shared secret | High security (open decision) |

Static credentials are fine for MVP server-to-server calls. HMAC signing is recommended for higher security later.

## Common Error Shape

```json
{
  "success": false,
  "error": {
    "code": "<MACHINE_READABLE_CODE>",
    "message": "<Human readable message>"
  }
}
```

Common codes:

| Code | HTTP | Meaning |
|---|---|---|
| `UNAUTHORIZED` | 401 | Authentication failed |
| `FORBIDDEN` | 403 | Authenticated but not allowed |
| `USER_NOT_FOUND` | 404 | Requested user does not exist |
| `VALIDATION_ERROR` | 422 | Request parameters invalid |
| `SERVER_ERROR` | 500 | Unexpected client-side server error |
| `RATE_LIMITED` | 429 | Client's API rate-limited MyVivahAI |

## Request Tracing

Every MyVivahAI → client request includes headers to aid debugging:

```
X-MyVivahAI-Request-ID: <uuid>
X-MyVivahAI-Platform-ID: <concise public platform id>
X-MyVivahAI-Signature: <signature when HMAC auth is enabled>
```

## Non-Functional Requirements

| Requirement | Value |
|---|---|
| Response Timewindow | < 2s per request (recommended timeout: 5s) |
| Response Size Limit | 1 MB |
| Encoding | UTF-8 JSON |
| Content-Type | `application/json` |
| Rate Limits | Configurable per platform |
