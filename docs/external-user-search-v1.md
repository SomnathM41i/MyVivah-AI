# External User Search API v1

This contract lets the MyVivahAI widget discover eligible users from the connected platform's full user base, including people who have never opened the widget. The client platform is authoritative for profile visibility and chat eligibility. MyVivahAI stores an identity reference only.

## Client endpoint

Configure one HTTPS `GET` endpoint per platform, such as `/api/v1/myvivahai/users/search`. MyVivahAI calls it server-to-server; the URL and credential are never sent to the browser. The endpoint must use an exact hostname explicitly allowed by the platform owner. Redirects are not followed. Production permits the default HTTPS port only, rejects IP literals/local names/private or reserved IPv4/IPv6 answers, and pins cURL to the validated public DNS address for that request to prevent DNS rebinding. Production search requires PHP cURL.

### Request

```http
GET /api/v1/myvivahai/users/search?q=riya&limit=20&cursor=opaque-value
Authorization: Bearer <platform-search-credential>
Accept: application/json
X-MyVivahAI-Request-ID: <uuid>
X-MyVivahAI-Platform-ID: <public-platform-id>
```

`q` is UTF-8, trimmed, 2–100 characters. `limit` is 1–20 (MyVivahAI always requests at most 20). `cursor` is omitted on the first request and otherwise is the exact opaque `next_cursor` previously returned. The authenticated client endpoint derives platform identity from `X-MyVivahAI-Platform-ID` plus its server-to-server credential, and requester identity from `X-MyVivahAI-Requester-ID`. That requester header is generated by MyVivahAI from the verified widget session; clients must not accept a browser-supplied requester ID.

### Success response

```json
{
  "success": true,
  "data": [
    {
      "external_user_id": "USR1001",
      "display_name": "Example User",
      "profile_photo_url": "https://cdn.example.com/photo.jpg",
      "profile_url": "https://matrimony.example/profile/USR1001"
    }
  ],
  "pagination": { "next_cursor": null, "has_more": false }
}
```

Only `external_user_id` and `display_name` are required. `profile_photo_url` and `profile_url` are optional HTTPS URLs. Do not return email, phone, birth date, caste, income, address, or full profile data. Results must be visible to the authenticated requester under the client's own privacy, block, membership, and chat-eligibility rules. Never include accounts from another platform.

### Errors

Return standard HTTP statuses: `401` invalid MyVivahAI credential; `403` requester/platform not allowed; `422` invalid query/cursor; `429` rate limited; `5xx` temporary service error. Error JSON may be `{ "success": false, "error": { "code": "UNAUTHORIZED", "message": "..." } }`. MyVivahAI does not expose upstream error bodies to widget users.

## MyVivahAI behavior and limits

The widget authenticates first with its short-lived, platform- and user-bound widget session. `GET /api/v1/widget/users/search?q=...&limit=20&cursor=...` requires `realtime_chat:read`; platform and requester identity come only from the verified token. MyVivahAI applies a per-platform search throttle, makes a single request with a 2-second connection and 5-second total timeout, caps response bodies at 256 KiB and result count at 20, validates every field, and does not retry. Failure returns `503 SEARCH_UNAVAILABLE`; conversations and message endpoints continue working.

Immediately before creating a conversation, MyVivahAI rechecks current eligibility by calling the same endpoint with `target_external_user_id=<selected id>&limit=1` (no `q` or cursor). The client applies its current privacy and eligibility rules and returns that exact user as the sole result when chat is still allowed, or an empty `data` array otherwise; the normal pagination object remains required. A missing result returns `403 CHAT_NOT_ALLOWED`; upstream failures return `503` and no conversation is created.

The widget displays normalized results and submits only a server-issued short-lived candidate token to conversation creation. The token binds platform, requester, target ID, and expiry. MyVivahAI creates the target's minimal identity mapping only after it verifies this token, then uses the existing deterministic conversation key. The recipient can later authenticate with their own widget session and discover the conversation. Profile display fields are transient and are not persisted.

Client API credentials are stored encrypted at rest. Audit logs record outcome, duration, result count, platform reference, and request ID only; never credentials, query text, result profile data, or authentication headers.
